# 通知与气泡里的名字、冷启动点通知 —— 修复与真机验收（2026-10-31）

## 一、用户反馈的两件事

1. （m45158）「聊天界面，通知中，对方的名称无论私聊还是群聊都是qq号，既不是网名，更不是备注或者群名」
2. （本轮自查）冷启动时点通知能不能直接进那个会话。

## 二、名字为什么会变成 QQ 号

两条互不相干的成因，必须都修：

| 位置 | 成因 | 修法 |
| --- | --- | --- |
| 通知（私聊） | MessagingStyle 的「发言人」传的是裸 QQ 号；系统在没有 conversationTitle 时拿最后一条消息的 sender 当标题 | 原生侧私聊的发言人直接用**会话标题**（`MessageNotifier.kt` 的 `who`） |
| 通知 + 气泡（群聊） | `msg_head` 字段 14（`qq8_push.dart:528` 的 `fromNick`）**经常为空**，适配器回落成 `'${m.fromUin}'` | 名字走**服务层名字缓存**；解析不出来宁可留空，绝不显示号码 |

名字的唯一可靠来源是列表接口：
- 好友：`Qq8Friend.displayName`（备注优先，`qq8_list.dart:77`）
- 群成员：`Qq8GroupMember.displayName`（群名片优先，`qq8_list.dart:421`）

## 三、改动清单（四态：已实现 + 离线已验证；真机待验收）

### 1) `lib/client_api/qq8_login_service.dart`（L3）
- 名字缓存**按语境分两张表**（m45402 之后的修正，见第三节之二）：
  - `Map<int, String> _friendNames`：uin → 好友备注/昵称；
  - `Map<int, Map<int, String>> _groupMemberNames`：gid → (uin → 群名片)。
- `String? displayNameOf(int uin)`：**私聊**名（好友备注优先），查不到返回 null。
- `String? groupMemberNameOf(int gid, int uin)`：**该群内**的名（群名片优先，退好友名）。
- `_rememberFriendName` / `_rememberGroupMemberName(gid, uin, name)`：空名字不写。
- `Future<void> ensureGroupNames(int gid)`：**同一群 10 分钟只拉一次**，异常静默（名字是装饰，绝不阻塞消息处理、绝不抛给上层）。
- `fetchFriendList` / `fetchGroupMembers` 末尾分别写两张表。

### 2) `lib/client_api/qq8_session_adapter.dart`（L3）
`senderName` 解析顺序：**按语境查缓存**（群消息 `groupMemberNameOf(groupCode, uin)`，私聊 `displayNameOf(uin)`）→ 消息自带昵称 → 本适配器见过的推送昵称 → 自己的昵称 → **空串**。
（原实现最后一档是 `'${m.fromUin}'`，就是号码的来源。）

### 2b) 为什么缓存要分表（真机 m45402）
用户：「为啥私聊其中一条信息显示的是对方群名」。第一版是一张全局 `uin → 名字` 表，群成员列表写入的是**群名片**，把好友备注覆盖掉了，于是私聊里显示成对方在群里叫的名字。真机数据侧证据：`chats/private_2089495846.jsonl` 里同一人先后出现 `senderName:"无道极法魔君"`（群成员刚拉过）与 `senderName:"净凾"`。

优先级同时定为 **服务层缓存 > 消息自带昵称**：备注/群名片是用户自己设的，且能纠正历史数据里写错的群名片。三处（适配器、气泡 `_senderLabelOf(m, chat)`、通知 `_resolveSenderLabel(message, chat)`）都必须带会话上下文查名字。

### 3) `android/.../MessageNotifier.kt`
`who`（MessagingStyle 的发言人）：
- 私聊 → 直接用会话 title；
- 群聊 → 用发言人，空则 `"群成员"`。

### 4) 名字补拉放在哪一层（重要）
**不放在协议推送路径里。** 第一版把 `ensureGroupNames` 写在适配器的群推送分支里，结果：
- `tool/qq8_session_adapter_selftest.dart` 6.5 直接红：「群消息推送不回执（多发了 1）」——每条群消息多一个包；
- 6.6 连带红：多出来的请求**吃掉了脚本传输的 seq**，后面的响应配不上（该文件的老坑：脚本帧 seq 必须等于下一次请求会拿到的号）。

现在改为 L4 层触发，协议路径只负责把消息交出去：
- `lib/ui/lifecycle/message_notify_scope.dart`：要弹群通知且 `senderName` 为空时补一次；
- `lib/ui/pages/home_page.dart`：`_openChat` 打开群会话时补一次，`.then` 里 `setState` 让气泡上的名字立刻出现。

### 5) 气泡显示名（`lib/ui/pages/home_page.dart` + `lib/ui/widgets/message_bubble.dart`）
- `MessageBubble` 新增 `String? senderLabel`（覆盖 message.senderName；气泡仍不认识 Riverpod）。
- `HomePage._senderLabelOf(ChatMessage m, Chat chat)`：先按会话语境查缓存（群用 `groupMemberNameOf(chat.rawId, uin)`、私聊用 `displayNameOf(uin)`）；查不到时昵称非空且非纯数字 → 用它；仍是号码就**返回空串**（气泡不画名字），不显示号码。
- 头像首字母同样用 `_senderLabelOf`。
- `_namesService()` 用 try/catch 读 provider：组件测试里没注入数据目录，读 `qq8LoginServiceProvider` 会抛 `UnimplementedError: qq8TokenStoreProvider 必须被 override`；名字是装饰，取不到就当没有（这条是 flutter test 抓出来的，见第四节）。

## 四、冷启动「点通知进会话」

原来 `MainActivity` 在 MethodChannel 注册的 `.also{}` 里主动 `channel.invokeMethod("opened", it)`。冷启动时 Dart 侧 handler 在 widget `initState` 才 `install()`，**早于它的 invoke 会被静默丢掉**。

改为拉取式：
- `MainActivity.kt`：只暂存 `pendingChatId`，新增 `"takePendingChatId"`（取完置 null），删掉主动 invoke。
- `lib/ui/platform/message_notifier.dart`：`Future<String?> takePendingChatId()`（MissingPluginException / PlatformException 返回 null）。
- `message_notify_scope.dart` initState：`unawaited(_consumePendingOpen())` → `_onOpenRequested`。
- 消费端 `home_page.dart`：`_pendingOpenChatId`(:84)、`_tryConsumePendingOpen()`(:250-266)、`ref.listen(pendingOpenChatProvider)`(:529-543)；chats 还没加载时保留等下次 build。

## 六、明确不支持 / 已知边界

- 历史已落盘的消息里，`senderName` 存的是当时的值（包括被写错的群名片）；**显示时缓存优先**，所以名字拉到后会以备注/本群群名片重画（重开会话 `setState`），但**不会回写 jsonl**（避免为了装饰改动消息存储）。
- 群成员列表拉取失败（离线/被限）时，群通知发言人显示「群成员」，气泡不显示名字——不显示号码。
