# 图片加载不出来 —— 官方 QQ / Telegram 对照与改造方案

日期：2026-10-31 · 范围：qqclient 聊天图片（含头像）加载链路 · 性质：**方案**（本轮不改代码）

## 0. 结论摘要

1. **根因不是「网络慢」，是「地址会过期 + 我们没有第二条取图通道」。** 真机抽 16 条消息直链逐条打：200 只有 2 条（12.5%），10 条 400（-5503007 download url has expired），4 条 404（群图全零路径，任何参数组合都取不到）。
2. **官方不用这条直链取图。** 官方聊天图片走 SSO 富媒体通道（ImgStore.GroupPicDown / LongConn.OffPicDown），响应里拿**新鲜的下载地址与票据**再取字节，所以官方用户看不到「链接过期」。直链只是消息元素里顺带的一段文本。
3. **Telegram 与官方 QQ 在客户端侧是同一套架构**：内存位图 LRU（带引用计数）→ 磁盘文件缓存（有文件就先渲染，不等网络）→ 单飞调度器（优先级 + 并发上限 + 滚出取消 + 分类重试）。我们只做了中间那层的一半，两头都是空的。
4. 因此方案分两条腿：**A 客户端取图架构对齐（立刻见效、不依赖协议）**；**B 协议补富媒体下载（根治，需真机抓包取证）**。A 无论如何都要做；B 让图片从「12.5% 能看」变成「几乎都能看」。

## 1. 实测数据（真机 25091RP04C / 包 com.example.qqclient / Android 16 API 36）

样本：从 /data/user/0/com.example.qqclient/files/accounts/*/chats/*.jsonl 抽 16 条图片直链，用设备 /system/bin/curl 逐条请求，两轮结果一致。

| 形态 | 数量 | 响应 | 说明 |
| --- | --- | --- | --- |
| 200 正常 | 2 | 922714B / 16446B | 元素里带了完整参数（rkey 未过期） |
| 400 过期 | 10 | body 70B：retcode -5503007 / retmsg download url has expired | rkey 有寿命，收到消息几小时后即废 |
| 404 全零路径 | 4 | gchatpic_new/0/0-0-MD5/0 | 元素里没有 16 / 15 / 34.30 片段，只剩 md5，该形态在 HTTP 侧永远取不到 |

补充探测（证明「换参数」这条路是死的）：

- 去掉 rkey：download?appid=1407&fileid=… → -5503010 ivalid rkey；&spec=1 → -5503037 ivalid spec or format；&rkey= → -5503011。**服务端只认带合法 rkey 的地址，而我们没有「重新申请 rkey」的协议请求。**
- 404 那条用 群号 / 发送者 / 大小 / 两个 md5（url 里的 04B111AA…EE 与文件名前 32 位 9bc951f7…0ba8）× 24~34 种参数组合全试 → **全 404**。这条样本就是真机截图里那个 1080×2337 的占位框（group_486045673，id=HPh36XyLLSYAAOcKSVbFQ2rkuxEB，time=1793374993000）。
- 16 条连发时，本来能成功的 download?...&spec=0 那条会变 400，单独重试必成 ⇒ CDN 对连发/并发有限流，客户端必须串行化或退避。

## 4. 两家收敛出的五条不变量

1. **磁盘文件是第一公民**：有文件 → 立刻渲染，永远不等网络；网络只是「补齐磁盘」的手段。
2. **每次取图只有一个在途任务（单飞）**：同一个 key 的多处 UI 共享一个 task，滚出屏幕就取消，不重复下载。
3. **调度有优先级和并发上限**：可见 > 预取 > 低优先；并发是显式数字（官方 5、TG 小文件 5 / 大文件 2），不是「有多少来多少」。
4. **失败是分类的、有次数上限的、可见的**：过期 / 不存在 / 限流 / 网络错误各有不同处置与不同 UI 文案；不存在无限重试。
5. **传输层用协议取图，不用元素里那串会过期的 URL**；并且先小图后大图（官方 act*SmallDownV1，TG thumbKey）。

## 6. 方案

### P0 观测与分类（0.5 天，零风险，先做）

目标：把「为什么这张图出不来」变成日志里一行能读的事实。没有这层，后面所有优化都是盲调。

- media_fetcher.dart：新增 `MediaFetchOutcome`（sealed：Ok(bytes) / HttpError(status, retcode, retmsg) / NetworkError(kind) / TooLarge / BadUrl），`fetch` 改为返回 Outcome；非 2xx 时**读 body 前 200 字节**解析 retcode/retmsg（现在直接 drain 掉了，等于把唯一证据丢掉）。
- 分类规则（写入代码常量，便于测试）：400 + retcode==-5503007 → expired；404 → missing；400 其他 → rejected（含 -5503037 spec）；429/503 → rateLimited；SocketException/超时 → network；超过 maxBytes → tooLarge。
- media_cache.dart：每个候选地址、每次尝试打一行结构化日志：`媒体 key=… cat=… cand=1/2 url=… → ok 922714B 412ms` / `→ expired(-5503007) 96ms`。用项目现有 Log，不用 print。
- 验收：真机重放 16 条样本，日志能逐条对上本文第 1 节的表；`dart analyze lib` 零 issue。

### P1 客户端取图架构对齐（1.5 天，立刻改善体验）

1. **负缓存（失败也记）**：MediaCache 增 `_failures[key] = {kind, atMs, cand}`；TTL 按类：expired 30 分钟、missing 7 天、rejected 30 分钟、network 30 秒、tooLarge 永久。ensure() 命中未过期失败 → 立即返回 null，不发请求。
2. **有限重试 + 退避**：network 重试 2 次（0.5s、2s）；rateLimited 重试 1 次（1.5s）；expired/missing 不重试（重试只会再拿一个 400/404）。重试在 MediaCache 内做，UI 无感。
3. **并发与优先级**：把全局信号量换成按 category 的信号量 —— 图片 4 并发、头像 6 并发、文件 2 并发；ensure() 增加 `priority`（visible / prefetch）。理由：16 条连发实测会把能成功的那条打成 400，串行化+少量并发是必须的。
4. **网络路径统一走缓存**：message_content.dart 的 `_networkOrPlaceholder` 删掉 `Image.network`，改为「ensure → 有文件 Image.file，没文件显示占位」。收益：单飞、负缓存、去重、离线可看全部生效；也顺带修掉「同一张图在列表和详情各下一遍」。
5. **状态 UI（对齐 URLDrawable 的 LOADING/SUCCESSED/FAILED）**：_ImageBlock 增 `_state`（loading / ready / expired / missing / failed）与 `_retry()`；文案：expired → 「图片链接已过期 · 点按重试」；missing → 「图片已失效」；failed → 「加载失败 · 点按重试」。点按重试 = 清该 key 的负缓存 + 重新 ensure；**这是给 P2/P3 争取时间的兜底体验**，不再假装在加载。
6. **头像**：telegram_avatar.dart 改走 MediaCache（category=avatar），失败可重试（点按或下次进入重试），仍保留首字母兜底。qlogo 通道本身健康（设备 curl 200 / 2642B，Cache-Control max-age=2592000），所以头像失败纯粹是我们没缓存。
- 验收：`flutter test` 全过 + 新增 3 个用例（负缓存命中不发请求 / expired 不重试 / 点按重试清缓存后再发一次）；真机：断网进会话，本地图仍显示，未缓存图显示明确失败态而不是空白。

### P2 直链刷新实验（0.5 天，先做实验再决定是否开发）

假设：**重新拉一次同一个会话/同一条消息，服务端会回一个带新 rkey 的元素片段。** 如果成立，10 条 400 里的大部分可以靠「重新申请地址」救回来，且完全不碰协议逆向（只是我们已有的拉消息接口）。

- 实验脚本（tool/，不进 lib）：对一条已知 expired 的消息，按其 seq 重新拉历史（或拉相邻窗口），打印旧/新的 16、15、34.30 三个片段与拼出的 url；再 curl 新 url 看是否 200。
- 若成立：MediaRef 增加 `resolveUrls` 回调（惰性刷新），MediaCache 在 expired 时调用一次，成功后清除负缓存并重试；日志记 `地址刷新成功`。
- 若不成立：直接把结论写进本文与 PITFALLS（「直链不可续期，只能走富媒体」），避免后人再试。

### P3 协议补富媒体下载（3~5 天，根治，前置=抓包取证）

**前置取证（半天，必须先做）**：设备有 root。用 tcpdump 抓官方 QQ 打开一张老群图的整个过程，筛出以 0x28 开头的 highway 帧，取出 GroupPicDown 的请求 pb（群号、md5、fid、大小）与响应 pb（下载地址、票据、ip:port）。同样抓一次私聊图（OffPicDown）。若拿不到帧（TLS/走长连），则本阶段降级为「不实现」，并在文档写明。

- 实现顺序：**群图 GroupPicDown → 私聊 OffPicDown**；复用 lib/kernel/wlogin8/qq8_image.dart 已有的组帧/解帧（0x28 + 头长 + 体长 + pb 头 + 数据 + 0x29）与 DataHighwayHead(1)/SegHead(2)，新增 Down 的请求/响应模型（不要复制 Up 的字段表，两者字段不同）。
- 响应若是「新鲜下载地址」：直接交给 P1 的下载器（此时 400 过期问题消失，因为地址是刚签的）；若是「票据 + 图床 ip:port」：走 highway 取流，落盘后复用 MediaCache 的 _store。
- 先小图后大图：如果响应里有小图地址（对应官方 act*SmallDownV1），先落小图立即显示，再取原图替换。
- 失败语义：协议失败（-5503007 类）→ expired，不重试；ssov 超时 → network，按 P1 退避。
- 风险：字段号单源、pb 结构未证实、可能要 0x544 类签名（这是已知 native 天花板，先确认抓包请求里是否带签名字段；带就说明此路走不通，需记录）。

### P4 内存层与预取（1 天，可选）

## 10. 一个必须记住的事实

用户看到的是「图片加载不出来」，但**代码里根本没有「图片加载」这个东西**：UI 直接 Image.network 打一个几小时后必失效的 URL，失败就画一个和未加载一样的占位。所以这不是修一个 bug，是补一层缺失的子系统 —— 这也正是两家官方客户端都单独养一个 ImageLoader/URLDrawable 模块的原因。
