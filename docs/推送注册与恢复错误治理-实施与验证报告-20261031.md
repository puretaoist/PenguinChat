## 3. 已实现清单（含证据）

### 3.1 P1 登录层封包（最高优先级候选）
- 官方 `msf/core/push/e.java:94-164`：register 的 body 是 WUP 原始字节，走 `sendSsoMsg`，不再套 OICQ 信封；oicq 参考 `base-client.ts:829-887` 也只有 `type===2` 才套。
- 我方 `lib/kernel/wlogin8/qq8_session.dart`：`sendLoginLayer` 改为**仅 `Qq8LoginType.login`(=2) 套 OICQ**；type 0（校时）/ 1（online 注册）/ 心跳 传原始 body。
- 测试：`tool/qq8_session_selftest.dart` 新增 1b 段——解 0x0A 登录层后断言 register body 首字节 `!= 0x02`、`decodeWrapper` 后 `[0]=10001 / [38]=1000 / [4]=11`；校时 body `00000000`；心跳 body 空。**登录（type=2）逐字节回归不变**。

### 3.2 P2/P3 配置回执
- 官方 `serverconfig/g.java:21-37`（resp tag1=type / tag2=seq / tag3=data）、`a/c.java:589-608`（仅 type3 回带 data）、`a/c.java:500-524`（先 dispatch 再统一回执）。
- 新增 `lib/kernel/wlogin8/qq8_config_push.dart`（纯 codec，无 IO）：`decodePushReq` 支持带/不带 4 字节长度前缀、seq 长整型、垃圾返回 null；`buildPushRespBody` 严格 tag1/tag2/tag3，type2 不塞 data。
- `lib/client_api/qq8_login_service.dart`：`_ackConfigPush` 先解码外层即回执，**type2 的 bigdata 解析放在其后单独 try**——内层坏不掉回执。
- 测试：`tool/qq8_config_push_selftest.dart` 16 项全过（含「请求 tag2=data 与回执 tag2=seq 相反」这种最容易写反的点）。

### 3.3 P4 注册响应三态
- `lib/kernel/wlogin8/qq8_register.dart`：删除「缺 tag2 时用 tag9(bCrashFlag)!=0 判成功」的兜底；新增 `parseResponseDetailed` → `ok / rejected / malformed`；缺 tag2 或解码失败 = malformed。
- `qq8_session.dart` 的 `registerWithOutcome` 按三态映射 confirmed/rejected/unconfirmed。
- 测试：`tool/qq8_register_selftest.dart` 47 项全过（缺 cReplyCode、bCrashFlag=1 必须是 false）。

### 3.4 P8 注册生命周期
- `_registerInFlight` 从裸 Future 改为 `({Qq8Session session, int epoch, Future<Qq8RegisterOutcome> future})`；只有同 session 且同 epoch 才复用；`_teardownConnection` 清空在途（旧会话不可复用）。
- QueryHB 触发的重注册结果统一提交 `_lastRegisterOutcome`；confirmed 清 `_pushChannelUnconfirmed`，unconfirmed 置位，供在线检查降级。
- 测试：`tool/qq8_login_service_selftest.dart` 第 11 段「注册三态」9 条断言。

### 3.5 S3 错误源头分类
- `Qq8LoginSnapshot` 新增 `networkIssue` 与 `stackTrace`。
- `_fail`：网络类异常 → `stage=disconnected` + `networkIssue=true` + 文案「网络不可用，请检查网络后重试」；非网络失败保持 failed 并带原栈。
- `reconnect()` 兜底分支改为 `offline = _snapshot.networkIssue || _networkUnavailable(text)`——**这是本轮抓到的回归**：只认归一后的文案会把断网算成 3 次服务端失败（5 轮断网后直接停住）。
- 测试：2f「断网 5 轮后仍能上线」、2g「服务端超时恰好 3 次」、2h「断网失败快照 disconnected+networkIssue 且无 failed」。

### 3.6 S4 消费者
- `qq8_session_adapter._onStage`：`networkIssue` 不发 `SessionFailure`（消除 ChatStore 每轮「会话层报错」）；同一失败按 `stage|resultType|error` 指纹去重；状态同而 reason 变也发 `SessionStateChanged`；`SessionFailure` 带回原栈。
- `qq8_providers.Qq8ConnectStatus` 增 `networkIssue`，断网时标签「等待网络恢复」；连接页网络提示改中性色（`qq8-network-hint`），`failed` 仍 `qq8-error` 红字。
- 测试：`tool/qq8_session_adapter_selftest.dart` 第 12 段（离线传输 + 真服务，订阅事件流断言无 SessionFailure、reason 含「网络」）。

## 8. 追加：四点复审的收口（同日晚）

用户批准的四点离线复审（"失败指纹去重会不会吞掉用户两次独立重试 / 断网静默的范围 / 切号或关闭后旧会话的迟到结果 / 注册异常分类会不会吞掉 authDead"），逐条落地如下。

| # | 风险 | 原行为 | 改法 | 回归用例 |
|---|---|---|---|---|
| ① | 指纹去重吞掉用户主动重试 | adapter 按 `stage\|resultType\|error` 去重，用户第二次点「登录」得到一字不差的失败 → 界面无任何反馈 | 引入**动作序号**：service 增 `_actionSerial`/`beginAction()`，快照新增 `actionSeq` 并在 `_emit` **产出瞬间**打戳；adapter 见 `s.actionSeq != _seenActionSerial` 就清空去重指纹；`qq8_providers._run`（所有 UI 动作的唯一入口，自动重连不经它）开头调 `beginAction()` | adapter §13：同一 service 上直接两次 `loginWithToken`（无票据→本地失败）只报 1 条 `SessionFailure`；经 `Qq8ConnectController` 点两次报 2 条 |
| ② | networkIssue 静默越界 | 断网快照不上报失败是对的，但若把静默做成"永久"，用户主动操作就得不到答复 | 静默只作用于**同一动作内**的重复快照；换动作（序号变）立刻恢复上报。用户主动操作必然新序号，故不会被静默 | 同上 §13；另 2f/2g/2h 断网与超时次数用例不变 |
| ③ | 切号/关闭后旧会话迟到结果污染新会话 | `_goOnline` 在 `await` 之后无条件 `_emit(online)`；关闭会话时那段 await 还在飞，回来会把已回到 idle 的状态再次点亮 | `_goOnline` 在 emit 前加 `if (!identical(_session, session) || epoch != _sessionEpoch) return;` | service §11 E：`_DelayTransport` 把「在线状态上报」一步拖 400ms，登录后 120ms 调 `close()` → 断言全程无 `online`、终态 idle，且确实经过了 connecting（防空转） |
| ④ | 注册异常分类吞掉认证终态 | `registerWithOutcome` 的 `on Object` 把 `Qq8ServerRetcodeException` 一律折成 `unconfirmed` → authDead(-10003) 变成"再注册一次"，无限重注册 | 前置一个 `on Qq8ServerRetcodeException catch (e) { if (e.authDead) rethrow; return unconfirmed; }`；`_registerInBackground` 捕获后走 `_markAuthLost` 停在 sessionExpired | session §11b：-10003 必抛且 `.authDead`；-1000 仍 unconfirmed。service §11 D：注册回 -10003 → 状态 sessionExpired、文案含「失效」 |

**一个必须记住的坑**：序号不能在 adapter 收到快照时才读 `service.actionSerial`。状态流是异步投递的，同一批快照会同一步送达，那时序号已推进——实测两条快照都读到 2，去重逻辑只报了 1 条失败。必须在快照**产生的那一瞬间**打戳（诊断脚本 `tmp/diag_dedupe.dart` 复现并定位，未提交）。
