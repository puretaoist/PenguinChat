### ①滚动记忆的取舍

- 还原用 `jumpTo` 而不是 `animateTo`：还原是「回到原样」，动画会让用户先看到底部再被拉上去。
- 放在 `addPostFrameCallback` 里：`ListView` 要等这一帧布局完才有正确的 `maxScrollExtent`。
- `_restoringScroll` 标志：还原过程中的 `_onScroll` 回调不许写回 map，否则把中间值记进去，下次更偏。
- `_backToChatList` / `dispose` 也存一次，避免「返回列表」这条路径丢掉位置。

### ④主题色的取色规则

- `default`（跟随主题）：暗色用调色板自带紫 #8774E1，亮色用自带蓝 #3390EC —— 不覆盖 base。
- 选具体颜色后：暗色下自己气泡跟着变色（TG 行为）；亮色下气泡仍是浅绿 #EEFFDE，只换强调色/未读徽标/选中行。
- 背景 `plain` 仍是原来的纯色底（暗近黑/亮浅灰），另四档是预设渐变。
- 全部经 `uiPrefsProvider` 落 `ui_prefs.json`（键 `accent` / `wallpaper`），坏值走白名单回默认。

## 五、回退修复：滚动记忆为什么在真机上「无效」（2026-11-03 22:00）

用户反馈（m63305）：「会话滚动记忆无效」。上一轮只验证了「群聊上翻 → 返回 → 进另一个会话 → 再回该群」
这一条路径，恰好通过，但其它路径不成立。补了回归测试后真因暴露：

### 真因：还原只试了一次，而那时列表往往还没准备好

`_restoreScroll()` 原来只注册**一次** `addPostFrameCallback`，然后 `jumpTo(target.clamp(0, maxScrollExtent))`。
但会话打开的那几帧里，消息是异步来的：

1. 空列表阶段画的是占位，**根本没有 ListView**，`_scrollController.hasClients == false` → 直接 return，
   后续没有任何重试 ⇒ 消息到了以后列表从 offset 0 开始画 ⇒ **永远停在顶部**；
2. 或者 ListView 已在、但内容还没铺开，`maxScrollExtent == 0` ⇒ `clamp(0.0, 0.0) == 0` ⇒ 同样停在顶部。

离线复现（`test/home_page_test.dart` 的「竖屏：聊天页记住上次滚动位置」用例）：打开会话后
`position.pixels == 0.0`、`maxScrollExtent == 1744.74` —— 列表在顶部，于是 `drag(0, 400)` 只能 overscroll，
pixels 恒为 0，断言 `greaterThan(100)` 当场红。

### 修法

- `_applyScroll(target, tries)`：**每帧重试**。`!hasClients` 或 `max <= 0` 时（最多 20 帧）继续等；
  就绪后 `jumpTo`（有记录）或 `animateTo(max)`（无记录，贴底）。
- `_restoringChatId`：还原期间禁止 `_onScroll` 写回缓存（否则把还原过程中的中间值记进去）。
- **停在底部记 `double.infinity` 而不是像素**：否则「离开后又有新消息」时，还原会落到旧像素位置，
  把最新消息显示成历史（另一类「记忆不对」）。`_applyScroll` 里 `!target.isFinite` 一律贴底。

### 验证

- 修前：`DBG0 pix=0.0 max=1744.7` → 用例失败；修后：`DBG0 pix=1712.0 max=1712.0`（打开即贴底），
  上翻到 1332 → 返回 → 再进 → 断言 `closeTo(1332, 1)` 通过。
- `flutter test test/home_page_test.dart` **18 全过**；全量 `flutter test` 见本轮门禁结论。

## 六、再修：「明明看到最新，再进来却不在最新」（2026-11-03 22:30，m63531）

第五节修好的是「还原根本没发生」（一次 postFrame 落空 → 停在顶部）。这一节是**另一种**不生效：
还原发生了，但落到的是**旧的底部**。

### 真因：`maxScrollExtent` 是估算值，且内容会继续长高

- `ListView.builder` 的 `maxScrollExtent` 由 SliverList 用**已布局子项的平均高度**外推未布局部分；
  打开会话那一刻只布局了十来行，算出来的底部是**估计值**；
- 图片、语音、长文本解码完成后行高变大，真实 `maxScrollExtent` 比刚才大几百像素；
- 原来贴底只做**一次** `jumpTo/animateTo(max)`，于是停在「估计出来的旧底部」——
  视觉上就是「离最新还差几条」。

### 修法：逐帧钉底（`_startBottomPin` / `_pinTick`）

- 打开会话贴底 / 发送消息后，连续若干帧（上限 90 帧 ≈1.5s）每帧检查 `pixels` 与 `maxScrollExtent`，
  差 >1px 就 `jumpTo(max)`。内容长多少就补多少。
- 钉底期间**不写**滚动缓存（`_pinningBottom` 也参与 `_onScroll` 的守卫），否则缓存里记的是中途值；
  并且 `_atBottom` 时缓存记 `double.infinity`（见第五节），保证「离开时在最新」下次仍回最新。
- 用户一动就放开：`_onScroll` 里 `if (_pinningBottom && !atBottom) _stopBottomPin();`。
  内容长高不会改变 `pixels`，所以不会误判成「用户上翻」。
- `dispose` 停钉，避免回调继续跑。

### 验证与诚实的边界

- 新增用例（`test/home_page_test.dart`）：「竖屏：离开时在最新，之后来了新消息，再进来仍是最新」——
  打开（贴最新）→ 返回 → `session.emit` 追加 30 条 → 再进 → 断言 `pixels == maxScrollExtent` 且最新一条在屏上。
- **要诚实**：这条用例覆盖的是「离开时在最新 → 再进来仍最新」这条语义；它**复现不了**估算漂移本身
  （测试里消息等高，`maxScrollExtent` 一开始就是准的）。估算漂移只有真机（图片/语音解码）才看得到，
  所以本轮的真机结论必须单独记录，不能用这条单测替代。
