# 新消息系统通知（2026-10-31）

> 目标：应用切到后台后收到消息，要像官方客户端一样弹一条系统通知；
> 点通知直接进那个会话。**前提已经具备**：推送链路实测可用
> （私聊 `MessageSvc.PushNotify`、群 `OnlinePush.PbPushGroupMsg`），
> 推送→落盘 79~331 ms（见 `docs/轮询策略调整-推送为主与群窗口短路-20261031.md` §6.4）。

## 1. 之前是什么状态

- 有前台服务（`KeepAliveService` + `ForegroundKeepAlive`），它唯一那条通知是
  **状态指示**（IMPORTANCE_LOW、不可滑走），不是消息提醒；
- 后台消息只落进 ChatStore，**用户毫无感知**——应用不在前台时等于收了个寂寞；
- 没有任何通知渠道、没有点击进会话的路径。

## 2. 分层落点（为什么这么切）

| 层 | 文件 | 职责 |
|---|---|---|
| L3 纯逻辑 | `lib/client_api/notify_policy.dart` | 「这条该不该弹」+ 标题/摘要拼装。纯 Dart，可离线自测 |
| L4 平台 | `lib/ui/platform/message_notifier.dart` | MethodChannel 封装（权限/发/撤/点击回调） |
| L4 接线 | `lib/ui/lifecycle/message_notify_scope.dart` | 订阅 ChatStore + 应用生命周期 → 调平台通道 |
| 原生 | `android/.../MessageNotifier.kt` + `MainActivity.kt` | 通知渠道、通知构建、点击回传聊天 id |

判据放 L3 的理由和 `deleted_placeholder.dart` 一样：**最容易写错的是"什么时候不该弹"**，
而它只依赖普通值；留在 UI 里就只能靠真机肉眼看，没法回归。

## 3. 判定规则（顺序即优先级）

| # | 条件 | 结论 | 原因码 |
|---|---|---|---|
| 1 | 自己发的（outgoing） | 不弹 | `outgoing` |
| 2 | 系统提示（入群/撤回…） | 不弹 | `system` |
| 3 | 会话免打扰（muted） | 不弹 | `muted` |
| 4 | 无可显示内容 | 不弹 | `empty` |
| 5 | 应用在前台 | 不弹 | `appVisible` |
| 6 | 消息时间早于 5 分钟 | 不弹 | `stale` |
| 7 | 其余 | **弹** | — |

第 6 条是这套设计的关键：**上线补拉 / 断网补齐会一次带回几十条历史消息**，
逐条弹就是通知轰炸。5 分钟阈值覆盖网络抖动与重连补齐，同时把补拉历史全部挡住。
实测推送→落盘 < 1 s，正常实时消息远低于阈值。

第 5 条：前台一律不弹（正在看这个会话当然不该弹；在看别的会话时官方客户端
也只在列表上加未读）。`activeChatId` 已经作为参数传进判定，留给将来做应用内横幅。

## 4. 通道协议

Dart → 原生（`qqclient/notify`）：

| 方法 | 参数 | 返回 |
|---|---|---|
| `ensurePermission` | — | bool（Android 13+ 弹一次系统权限框；13 以下恒 true） |
| `notify` | chatId / title / text | null |
| `cancelAll` | — | null（只撤本通道发过的，不碰保活那条常驻通知） |

原生 → Dart：`opened` / 参数 chatId —— 用户点了某条消息通知。

点击进会话的接线：作用域把 chatId 写进 `pendingOpenChatProvider`（L3 的 StateProvider），
`HomePage` 在 build 里 `ref.listen` 消费并 `_openChat`（排到下一帧，避免 build 期 setState）。
`HomePage` 是唯一持有"当前选中会话"的地方，所以只能由它落地。

冷启动时序：通知点击可能发生在 Dart 通道就绪**之前**，MainActivity 把 chatId
先存进 `pendingChatId`，等通道注册时补发；之后点击走 `onNewIntent` 直接 invoke。
两种情况都收敛到 `handleChatIntent`，取完即删 extra，避免重进 activity 再打开一次。

## 5. 通知形态

- 渠道 `qqclient.messages`：IMPORTANCE_HIGH（横幅 + 声音 + 角标），与保活渠道分开；
- 通知 id = `chatId.hashCode()`：**同一会话的多条消息合并成一条**（后覆盖前），
  不同会话各一条 —— 与官方/微信行为一致，也避免刷屏；
- 标题：私聊=对方昵称；群聊=`群名 · 发言人`（只显示群名看不出谁说的，
  只显示发言人不知道是哪个群）；
- 正文：消息文本摘要（已有 `[图片]`/`[表情]` 占位），空文本兜底「新消息」，超 120 字截断；
- 自动清除、点击自动消失；回到前台时 `cancelAll()` 把残留通知一次清掉。

## 6. 离线验证

`tool/notify_policy_selftest.dart` —— 23 项，全过：

- 6 条排除项各一例（含"前台但在看别的会话"）；
- 3 条正例（实时/30 秒前/恰好 5 分钟边界）+ 时钟偏差（未来时间）不算过期；
- 补拉场景（3 小时前）不弹；
- 判定顺序：多条件同时成立时报最贴近用户意图的原因码；
- **64 种布尔×时效组合穷举**，只有"非自己发、非系统、非免打扰、后台、新鲜、有内容"这一种会通知；
- 摘要（空文本/原文/超长截断 121 字符）与标题（私聊/群/缺发言人）各例。

门禁：`dart analyze lib` No issues；`bash tool/run_all_selftests.sh` 全过；`flutter test` 全过。

## 7. 真机验收（待做）

1. 装包后首次进应用应弹一次通知权限框（Android 13+）；拒绝时日志记
   「通知权限: 未授予（消息仍会收，但不弹通知）」，消息照常落盘；
2. 把应用切后台，让对端发一条私聊 → 通知栏出现一条「对方昵称 / 正文」；
3. 同会话连发三条 → 仍是**一条**通知（内容是最新那条）；
4. 点通知 → 应用被唤起并直接进入该会话；
5. 回到前台 → 通知全部消失；
6. 杀进程重开后，若从补拉带回历史消息 → **不应**产生任何通知（stale 过滤）。

## 8. 四态口径

- **已实现**：判定策略、MethodChannel 三方法、通知渠道与合并、点击进会话（含冷启动补发）、
  回前台清理。
- **离线已验证**：23 项策略断言 + analyze/selftest/flutter 全绿。
- **真机未验证**：权限弹框、后台弹通知、通知合并、点击进会话、回前台清理、补拉不弹。
- **明确不支持**：应用被划掉（stopWithTask=true）后继续收消息——那需要把服务改成
  不被任务清理，且要做 Application 级常驻连接，属于另一个量级的改动，本版不做
  （详见 AndroidManifest 里 `stopWithTask` 的注释）。

## 9. 与 Telegram 通知实现的对照（2026-10-31 追加）

参考源码：`telegram-src/TelegramAndroid/TMessagesProj/src/main/java/org/telegram/messenger/NotificationsController.java`。

**照搬的**：

| Telegram 做法 | 出处 | 本项目 |
|---|---|---|
| 每个会话一条通知，id 由会话 id 派生 | :5012 `(int) dialogId + (int)(dialogId >> 32)` | `chatId.hashCode()` |
| MessagingStyle（发言人 + 时间，群聊带会话标题） | :5268-5277、:5642-5656 | 已用 `NotificationCompat.MessagingStyle`，群聊 `setConversationTitle` + `setGroupConversation(true)` |
| 多会话分组 + 汇总（children 不各自响） | :4646-4647、:5675-5676、:5762-5763 | 已用 `setGroup` / `setGroupSummary` / `GROUP_ALERT_SUMMARY` + InboxStyle 汇总 |
| 撤通知逐个 cancel，不用 cancelAll | :3329-3452 各处 `cancel(id)` | 逐个 `cancel(id)` + 汇总 id |
| 划掉通知后不再为旧消息重弹 | :4908 `messageOwner.date <= dismissDate` | 用 Dart 侧 5 分钟新鲜度窗口（notify_policy.dart 的 `stale`）达成同样效果 |
| 后台才提醒，前台/正在看该会话不打扰 | :1239-1244 `dialogId == openedDialogId && isScreenOn` | 见下面的差异 |

**刻意不照搬的（以及原因）**：

- **前台判据更粗**：Telegram 只在"当前会话就是这个会话且屏幕亮"时跳过，其他前台场景走应用内横幅；
  本项目没有应用内横幅，前台一律不弹（`notify_policy.dart` 的 `appVisible`）。宁可少弹，不要打扰。
- **不设"划掉即静音该会话"的 dismissDate**：那需要 `NotificationDismissReceiver`（广播 + 持久化
  dismissDate），收益是"用户已经划掉的会话不因补拉又冒出来"——已有 5 分钟窗口覆盖主要场景。
- **不做回复/标记已读 action**：Telegram 的 `NotificationCompat.Action`（:5707-5712）走
  `NotificationCallbackReceiver` 直接发消息，这要求原生侧掌握发送链路；本项目发送全在 Dart，
  为了一个通知按钮把协议层挪到原生不值得。
- **不做每会话独立通知渠道/声音/振动**（Telegram :4116-4135 按会话建 channel）：渠道一多，用户在系统设置里
  就得自己挑；本项目只有一个 `qqclient.messages` 渠道，行为可预期。
- **不做角标/启动器快捷方式**（`NotificationBadge`）。

**唯一无法回避的差异**：应用被划掉（`stopWithTask=true`）后收不到推送，Telegram 靠系统级 push 服务；
本项目没有那层基础设施，见 §8「明确不支持」。
