# 语音消息 V2：录音 + 上传 + 发送（QQ 8.2.11 官方链路对齐）

> 日期：2026-11-01　范围：`com.puretaoist31.penguinchat`（自实现协议线路）
> 前置：V1（接收 + SILK 解码播放）见 `docs/语音消息-V1播放-20261101.md`
> 口径：本文所有"官方"结论均来自 8.2.11 APK 反编译，出处见每条后的类/方法/行号。

## 1. 链路总览（官方与我们的三步完全同构）

    按住说话 → AudioRecord(PCM16/16k/单声道) → SILK v3 编码(.slk)
      → ① 0x346 APPLY_UPLOAD（SSO 长连接）拿 ip/port/uuid/upload_key
      → ② HTTP POST 原始 SILK 字节到 /qqcommfileupload
      → ③ MessageSvc.PbSendMsg，msg_body.rich_text.ptt（RichText 第 4 字段）

与我们 V1 已有的下载/解码方向相反，但容器、SILK 帧格式、ptt 结构化字段共用同一套解析。

## 2. 官方取证结论（实施依据）

### 2.1 申请上传（`cmd0x346`，命令 `PttCenterSvr.pb_pttCenter_CMD_REQ_APPLY_UPLOAD-500`）
- 外层 `cmd0x346.ReqBody`（jadx `tencent/im/cs/cmd0x346/cmd0x346.java:545`）：`1=uint32_cmd(500)`、`2=uint32_seq`、`7=msg_apply_upload_req`、`101=business_id(17)`、`102=client_type(104)`、`99999=msg_extension_req`。
- `ApplyUploadReq`（:267）：**字段号是十位段**，`10=sender_uin`、`20=recver_uin`（群里填群号）、`30=file_type(2)`、`40=file_size`、`50=file_name`、`60=bytes_10m_md5`（16 字节原始 MD5，不是 hex）。
- `ExtensionReq`（:431）：`1=uint64_id(3)`、`2=uint64_type(bdh cmdid)`、`90200=ptt_format`、`90400=net_type`、`90500=voice_type`、`90800=ptt_time(秒)`。**官方每次都发**，缺它等于子业务未知。
- 回执 `ApplyUploadRsp`（:309）：`10=int32_ret_code(0 成功)`、`20=ret_msg`、`60=upload_ip`、`70=upload_domain`、`80=upload_port`、`90=bytes_uuid`、`100=bytes_upload_key(=upload_key)`、`110=bool_file_exist`、`120=pack_size`。**C2C 回执没有 file_id**（file_id 只有群）。
- 失败码：9311 / 9044（`Layuw.a(Layqc;Layqb;)V`）；成功还要求 ukey 与 ip 非空。

### 2.2 HTTP 上传（`Layow.a([B)` 拼 URL、`Laylx.a([B)` 发 POST）
    http://{ip或domain}[:port，80 省略]/qqcommfileupload?ver=100
      &ukey={upload_key}&filekey={32位md5hex}&filesize={n}
      &bmd5={当场对 body 再算的 md5hex}&range=0&voice_codec=0

- 方法 **POST**（`Layoo->a=1` → `Layps` 里 GET/POST 分支）；body 就是**原始 SILK 字节**，不包 multipart、不加额外头。
- 只显式设两个头：`Range: bytes=0-`、`Accept-Encoding: identity`；**没有 Content-Type、没有 upload-key 头**（ukey 走 query）。
- 成功判据：响应头 `User-ReturnCode` ∈ {0, 9223372036854775807}。
- `uuid` **不进 URL**，只写进 `RichText.ptt.bytes_file_uuid`。
- 群 PTT 不是这条路：`PttStore.GroupPttUp`(cmd0x388 subcmd=3) → TryUpPttRsp 拿 ip/port/ukey/file_key → **BDH** 上传，URL 形如 `/?ver=4679&...&mType=pttGu`。本实现暂不做。

### 2.3 消息体（`im_msg_body.Ptt`，`im_msg_body.java:601-626`）
| # | 字段 | C2C | 群 |
|---|---|---|---|
| 1 | uint32_file_type | 4 | 4 |
| 3 | bytes_file_uuid | ✔ | ✔ |
| 4 | bytes_file_md5 | ✔（16B 原始） | ✔ |
| 5 | bytes_file_name | md5hex + `.amr` | urlAtServer 或 md5hex+".amr" |
| 6 | uint32_file_size | ✔ | ✔ |
| 7 | bytes_reserve | ✔（C2C 用 7） | — |
| 8 | uint32_file_id | — | ✔ |
| 18 | bytes_group_file_key | — | ✔ |
| 19 | uint32_time | — | ✔（秒） |
| 20 | bytes_down_para | directUrl（可 ""） | directUrl |
| 21 | uint32_format | — | ✔（voiceType） |
| 22 | bytes_pb_reserve | — | ✔ |

- `RichText`（:739）：`2=elems(repeated)`、**`4=ptt`** —— ptt 与 elems 平级，不是一个 Elem（这行最容易写错）。
- 发送命令只有一个 `MessageSvc.PbSendMsg`，`PbSendMsgReq` **没有 msgtype 字段**；`msgtype=-2002` 是接收侧 `MsgHead.msg_type` 的概念。
- 官方 `MessageForPtt.getRichText()`（`data/MessageForPtt.java:352-408`）逐字确认：`urlAtServer` 只在**上传完成回调**里写入 ⇒ 空 uuid 无法定位文件，**必须真上传**。

已知取舍：
- `down_para` 传空串（官方允许空，接收端可走 0x346 APPLY_DOWNLOAD 取地址）。
- `bdh_cmd_id` 在申请体里传 500（官方取值域 {500,102,104,105,101,103,114}，C2C 语音需真机确认）。
- `net_type` 暂固定 1。
- 上传是**单请求整包**（不分片、无 range 续传）；语音几 KB～几百 KB，够用。
- **不支持**：群语音（走 0x388+BDH）、AMR（voiceType=0）、波形上传（`general_flags.bytes_pb_reserve` 里的 ptt_waveform）、转文字（0x355）。

| 事实 | 数值/形态 |

### 5.5 一处必须记住的坑：protobuf fixed32 的字节序

bigdata 回包里的 IPv4 是 **protobuf fixed32（wiretype 5，小端）**。
`Qq8Pb.decode` 原来只支持 varint / length-delimited，遇到 fixed32 直接抛
`未支持的 wiretype 5（tag=2）`；补上后还要注意：`u32ToIp` 是给 varint 携带的
**大端数值**用的，拿它解 fixed32 会把 IP 写反（157.148.63.103 解成 103.63.148.157），
必须用 `_ipv4OfFixed32`（低字节是第一段）。
