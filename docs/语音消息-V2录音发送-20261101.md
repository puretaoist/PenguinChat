# 语音消息 V2：录音 + 上传 + 发送（QQ 8.2.11 官方链路对齐）

> 日期：2026-11-01　范围：`com.puretaoist31.penguinchat`（自实现协议线路）
> 前置：V1（接收 + SILK 解码播放）见 `docs/语音消息-V1播放-20261101.md`
> 口径：本文所有"官方"结论均来自 8.2.11 APK 反编译，出处见每条后的类/方法/行号。

## 1. 链路总览（官方与我们的三步完全同构）

    按住说话 → AudioRecord(PCM16/16k/单声道) → SILK v3 编码(.slk)
      → ① 0x346 APPLY_UPLOAD（SSO 长连接）拿 ip/port/uuid/upload_key
      → ② HTTP POST 原始 SILK 字节到 /qqcommfileupload
      → ③ MessageSvc.PbSendMsg，msg_body.rich_text.ptt（RichText 第 4 字段）

与我们 V1 已有的下载/解码方向相反，但容器、SILK 帧格式、ptt 结构化字段共用同一套解析。

## 2. 官方取证结论（实施依据）

### 2.1 申请上传（`cmd0x346`，命令 `PttCenterSvr.pb_pttCenter_CMD_REQ_APPLY_UPLOAD-500`）
- 外层 `cmd0x346.ReqBody`（jadx `tencent/im/cs/cmd0x346/cmd0x346.java:545`）：`1=uint32_cmd(500)`、`2=uint32_seq`、`7=msg_apply_upload_req`、`101=business_id(17)`、`102=client_type(104)`、`99999=msg_extension_req`。
- `ApplyUploadReq`（:267）：**字段号是十位段**，`10=sender_uin`、`20=recver_uin`（群里填群号）、`30=file_type(2)`、`40=file_size`、`50=file_name`、`60=bytes_10m_md5`（16 字节原始 MD5，不是 hex）。
- `ExtensionReq`（:431）：`1=uint64_id(3)`、`2=uint64_type(bdh cmdid)`、`90200=ptt_format`、`90400=net_type`、`90500=voice_type`、`90800=ptt_time(秒)`。**官方每次都发**，缺它等于子业务未知。
- 回执 `ApplyUploadRsp`（:309）：`10=int32_ret_code(0 成功)`、`20=ret_msg`、`60=upload_ip`、`70=upload_domain`、`80=upload_port`、`90=bytes_uuid`、`100=bytes_upload_key(=upload_key)`、`110=bool_file_exist`、`120=pack_size`。**C2C 回执没有 file_id**（file_id 只有群）。
- 失败码：9311 / 9044（`Layuw.a(Layqc;Layqb;)V`）；成功还要求 ukey 与 ip 非空。

### 2.2 HTTP 上传（`Layow.a([B)` 拼 URL、`Laylx.a([B)` 发 POST）
    http://{ip或domain}[:port，80 省略]/qqcommfileupload?ver=100
      &ukey={upload_key}&filekey={32位md5hex}&filesize={n}
      &bmd5={当场对 body 再算的 md5hex}&range=0&voice_codec=0

- 方法 **POST**（`Layoo->a=1` → `Layps` 里 GET/POST 分支）；body 就是**原始 SILK 字节**，不包 multipart、不加额外头。
- 只显式设两个头：`Range: bytes=0-`、`Accept-Encoding: identity`；**没有 Content-Type、没有 upload-key 头**（ukey 走 query）。
- 成功判据：响应头 `User-ReturnCode` ∈ {0, 9223372036854775807}。
- `uuid` **不进 URL**，只写进 `RichText.ptt.bytes_file_uuid`。
- 群 PTT 不是这条路：`PttStore.GroupPttUp`(cmd0x388 subcmd=3) → TryUpPttRsp 拿 ip/port/ukey/file_key → **BDH** 上传，URL 形如 `/?ver=4679&...&mType=pttGu`。本实现暂不做。

| # | 字段 | C2C | 群 |
|---|---|---|---|
| 1 | uint32_file_type | 4 | 4 |
| 3 | bytes_file_uuid | ✔ | ✔ |
| 4 | bytes_file_md5 | ✔（16B 原始） | ✔ |
| 5 | bytes_file_name | md5hex + `.amr` | urlAtServer 或 md5hex+".amr" |
| 6 | uint32_file_size | ✔ | ✔ |
| 7 | bytes_reserve | ✔（C2C 用 7） | — |
| 8 | uint32_file_id | — | ✔ |
| 18 | bytes_group_file_key | — | ✔ |
| 19 | uint32_time | — | ✔（秒） |

| 21 | uint32_format | — | ✔（voiceType） |

- `RichText`（:739）：`2=elems(repeated)`、**`4=ptt`** —— ptt 与 elems 平级，不是一个 Elem（这行最容易写错）。
- 发送命令只有一个 `MessageSvc.PbSendMsg`，`PbSendMsgReq` **没有 msgtype 字段**；`msgtype=-2002` 是接收侧 `MsgHead.msg_type` 的概念。
- 官方 `MessageForPtt.getRichText()`（`data/MessageForPtt.java:352-408`）逐字确认：`urlAtServer` 只在**上传完成回调**里写入 ⇒ 空 uuid 无法定位文件，**必须真上传**。

### 5.5 一处必须记住的坑：protobuf fixed32 的字节序

bigdata 回包里的 IPv4 是 **protobuf fixed32（wiretype 5，小端）**。
`Qq8Pb.decode` 原来只支持 varint / length-delimited，遇到 fixed32 直接抛
`未支持的 wiretype 5（tag=2）`；补上后还要注意：`u32ToIp` 是给 varint 携带的
**大端数值**用的，拿它解 fixed32 会把 IP 写反（157.148.63.103 解成 103.63.148.157），
必须用 `_ipv4OfFixed32`（低字节是第一段）。

## 2026-11-02 修正：不要给 down_para 填 1200 拿到的地址

原实现（见 C114）在上传完成后调 0x346 子命令 1200 换直链，并把结果写进 `RichText.ptt.20(down_para)`。
真机对端仍显示「消息已过期」。PC 探针复查后确认两点（详见 docs/PITFALLS.md 的 C115）：

1. `ApplyDownloadReq` 的字段号旧代码写错了（`bytes_uuid` 应为 20、`owner_type` 应为 30），
   服务端拿不到 uuid，回包里的 URL 是 `fileid=` 空的坏链，GET 它必然 `-5503023 appid is not match`。
2. 字段改对后，1200 给的是 BDH 下载地址（`/?ver=2&rkey=…`），它不是给普通 GET 用的；
   官方发送端本身也不填 down_para，下行 directUrl 由服务端投递时生成。

现行为：`buildApplyDownloadBody` 字段已修正（供后续 BDH 下载/回读用），`sendVoice` 不再调它，
`downPara` 固定空串。这样对端走自己的「1200 + BDH 下载」链路，不会因为我们塞的坏 URL 判过期。

遗留：我方**接收**语音仍未实现 BDH 下载（PicDown 帧），所以本地播放不了收到的语音；
这一步需要下一轮做（1200 已能拿到可用 rkey，缺的是 httpconn 下载帧与落盘）。

## 2026-11-03 更正：对端「消息已过期」的根因是**上传通道**，不是元素字段

对端（官方 QQ）收到我方语音后仍提示「消息已过期」。本轮按官方 8.2.11 反编译逐字段复核，
结论是**我方 ptt 元素完全正确，问题出在文件被上传到了错误的存储**。

### 1. 元素字段（已逐字核对，无误）
- RichText.ptt fieldMap（analysis/_decompiled/jadx-main/sources/tencent/im/msg/im_msg_body.java:601）：
  1 file_type、2 src_uin、3 file_uuid、4 file_md5、5 file_name、6 file_size、7 reserve、
  8 file_id、18 group_file_key、19 time、20 down_para、21 format、22 pb_reserve。
- C2C 只发 {1=4, 3=uuid, 4=md5(16B), 5=md5hex+".amr", 6=size, 20=directUrl, 7=reserve}
  （MessageForPtt.getRichText() C2C 分支只 set 这几个；8/18/19/21/22 是群语音才发）。
- 我方 buildPttElem 实测 hex：0804 1a24<36B uuid> 2210<16B md5> 2a24<"md5.amr"> 30c253(6=10690) a20100(20="")
  ⇒ 与官方一致。漫游回读到的那份副本缺 6(file_size)、且带服务端补的 2=0 与 47B reserve，
  是服务端裁剪后的副本，**不能当判据**。

### 2. 真正的差异：只有官方 HTTP 通道才会把 uuid 与文件绑定
- 官方 C2C 上传（Layow.a([B)）：POST http://<upload_ip>[:port]/qqcommfileupload?ver=100&ukey=…&filekey=<md5hex>&filesize=…&bmd5=<MD5(body)>&range=0&voice_codec=0，
  头只有 Range: bytes=0- 与 Accept-Encoding: identity，成功判据 User-ReturnCode ∈ {0, 9223372036854775807}。
- 我方此前走的是 bigdata highway（HttpConn.0x6FF）：文件落到 BDH 存储，**没有与 uuid 绑定**，
  对端凭 uuid 换链自然拿不到 → 报「消息已过期」。
- ApplyUploadRsp 在 8.2.11 里根本没有 fileid/rkey 字段（V2/V3 也只加了 https 相关），
  所以不存在「只发 md5 让服务端自己找文件」的路径。

### 3. 本机网络事实（2026-11-03 实测，PC 与手机一致）
| 目标 | 端口 | 结果 |
| --- | --- | --- |
| 11.180.101.107 / 11.142.86.199 / 11.187.146.77 / 11.187.144.132 | 80 / 15000 / 14000 | **全部 closed**（PC SocketException；手机 nc 超时） |
| 112.86.240.103 | 80 / 15000 / 14000 | **全部 OPEN**（我方 highway 上传就打到这里） |

⇒ 在这条网络上官方 HTTP 上传通道不可达，只能回落 bigdata。

### 4. 本轮改动（lib/client_api/qq8_login_service.dart）
- sendVoice 改为**先官方 HTTP、失败再回落**：_uploadPttOfficialFirst() 依次试 0x346 回执的
  host → ip_list → dns（Qq8PttHttp.upload，就是官方 URL/头），全部失败记
  「官方 HTTP 上传通道全部不可达，回落到 bigdata（对端可能显示已过期）」再走 _uploadPttViaHttpConn。
- 这样在任何能连上 11.x 的网络（例如能直连移动节点的蜂窝网络）里，语音就能真正被对端播放。

### 5. 已知未解决
- 本机 Wi-Fi 到 11.x 不可达 ⇒ 本次真机发送仍会回落，对端仍显示已过期（受网络阻断，非代码问题）。
- 接收侧 BDH 下载（1200 拿到 /?ver=2&rkey=… 之后的 PicDown 帧）仍未实现，
  真机日志可见 kind=rejected status=400（BDH 地址被当普通直链 GET）。


## 6. 2026-11-03 更正：bigdata 上传其实一直失败（error_code=372）

前五节把「HTTP 200 / ack code=0」当成上传成功，**这是误判**。本节记录真实现状与取证。

### 6.1 判据读错了字段

- 回包帧结构：`28 | u32be 头长 | u32be 体长 | 头PB | 数据 | 29`，头是 `RspDataHighwayHead`
  （官方 `com/tencent/mobileqq/highway/protocol/CSDataHighwayHead.java:138` initFieldMap）：
  `1 basehead`、`2 seghead`、`3 uint32_error_code`、`4 allow_retry`、`5 cachecost`、
  `6 htcost`、`7 bytes_rsp_extendinfo`、`8 timestamp`、`9 uint64_range`、`10 is_reset`。
- 旧 `Qq8PttHighway.ackCode` 读的是 `f2.f1`（SegHead 的 `uint32_serviceid`，服务端恒回 0），
  所以永远「成功」。真机/PC 实测同一条回包：`f3 = 372`、`f7 extendinfo = 空`、`f9 range = 0`。
  对比 TIM 官方上传回包（`_ptt_tim2.pcap`）：`f3 = 0`、seghead `f7 flag = 1`、`f9 range = 3547`（=整个文件）。
  ⇒ `range = 0` 说明**服务端一个字节的正文都没收下**，文件没有登记到 CDN。
- 已修正：`ackCode` 改读 `f3`，新增 `ackExtendInfo` 取 `f7`；上传失败不再抛断发消息流程，
  只记 `PTT 上传失败（对端将显示已过期…）`。

### 6.2 不是 ext 的错

对同一个 SILK 文件试了 5 种 ext（空 / `{6: 0x346 回执}` / `+10:1MB` / 加 uuid / 加 `11:{1:20B}`）
以及 TIM `sendFileByBDH` 那套 **ext = 0x346 ReqBody 原文（116B）**：raw TCP 与 httpconn 两条路
回包**全是 `f3=372`、extendinfo 空、range=0**；把正文去掉只发头（presend 形态）则变 `f3=331`。
⇒ 372/331 与 ext 内容无关，是「这次上传请求服务端不认」的通用结果码。

### 6.3 官方真正的上传通道在这儿（8.9.50/TIM 反编译）

- TIM `Lcom/tencent/mobileqq/transfile/C2CPttUploadProcessor;`：
  `sendFileByBDH()` 建 `cmd0x346 ReqBody{1:500, 2:seq, 7:ApplyUploadReq{10 sender,20 recver,30 file_type=2,40 file_name,50 file_size,60 10m_md5}, 101:17, 102:104, 99999:ExtensionReq}`
  当 ext 提交 highway 事务；`doOnSendSuc([B)` 把回调字节 `mergeFrom` 成 `cmd0x346 RspBody`，
  取 `msg_apply_upload_rsp.bytes_uuid` → `set uuid from BDH `（这与我方从 0x346 直接拿 uuid 不同）。
- 官方 pcap 里真正的上传帧（`_ptt_tim2.pcap`，`POST /cgi-bin/httpconn?htcmd=0x6FF0087&uin=…` 到
  `36.155.208.117:14000`）的 **ext 是 848B protobuf**：`1`=fileid(99B ASCII)、`2`=rkey(359B)、
  `5`=4×`Addr{1:{1:ip_type,2:ip},2:port}`、`6`=`DownloadInfo{1:FileInfo{1:size,2:md5hex,3:raw md5,4:"<md5hex>.amr"},2:fileid,4:upload_time,5:604800}`、
  `10`=1048576、`11:{1:20B}`。⇒ **官方上传时 fileid/rkey/下载节点都已经有了**，
  说明它在上传之前有一次「presend/登记」把这个文件登记进了 CDN。
- 8.9.50 的 `ApplyUploadRsp`（V1/V2/V3）字段里**没有 fileid、没有 rkey**（只有 uuid / upload_key /
  ip / port / ip_list / dns / pack_size；V3 多 mediaplatform key 与 https 域名）。
  ⇒ fileid/rkey 只能由**服务端在文件真正落地后**返回（大概率在 presend 上传的回执 extendinfo 里）。

### 6.4 卡点：上传前置节点全部不可达

- 0x346 回执给的 `upload_ip` / `ip_list` 全是 `11.180.x / 11.187.x / 30.46.x`：
  PC 与手机（同一 Wi-Fi）实测 **80/14000/15000/8080 全 TIMEOUT**。
- 只有 `112.80.145.223` / `36.155.208.117`（TIM 抓包里那个媒体平台节点）80/14000/15000 可连，
  但对它们 POST `/qqcommfileupload` 一律 `Connection closed before full header`（不是这个服务）。
- 想拿「媒体平台地址」必须走 `ApplyUploadReqV3`（字段 19）+ `uint32_flag_support_mediaplatform=1`（字段 200）。
  我方试了 7 种 V3 组合（cmd 500/501、带/不带 101/102/200/99999），服务端**全部回 0 字节**
  （V1 同参数正常回 324B）⇒ V3 的封装/命令号还没对上，**这是下一步唯一有希望的方向**。

### 6.5 现在的行为（诚实降级）

- 语音照常**发出**（`PbSendMsg` code=0），但音频文件没有落到 CDN，对端点开会显示「消息已过期」。
- 日志会明确写：`httpconn 回包异常 status=200 code=372 …` 与 `PTT 上传失败（对端将显示已过期…）`。
- **接收方向不受影响**：官方发来的语音带 fileid+rkey，能正常下载播放（见 `docs/语音换链-ptt-uuid-20261103.md`）。
