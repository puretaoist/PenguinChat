## 1. 断网方法（比飞行模式更可控）

飞行模式会同时掐掉发送方，无法在"我方离线"的窗口里制造入站消息。改用 per-uid 防火墙：

```bash
ADB=C:/Users/Administrator/AppData/Local/Android/Sdk/platform-tools/adb.exe
# 查 uid（com.example.qqclient → 10372）
"$ADB" shell pm list packages -U | grep qqclient
# 断网（只掐这个 uid，TIM / 系统网络照常）
"$ADB" shell "su -c 'iptables -I OUTPUT 1 -m owner --uid-owner 10372 -j REJECT'"
# 恢复
"$ADB" shell "su -c 'iptables -D OUTPUT -m owner --uid-owner 10372 -j REJECT'"
```

判定真的断了：日志出现 `等待响应超时（seq=…）` → `断线恢复：网络不可用（stage=disconnected），15s 后再试`。
判定真的恢复：`断线恢复成功（第 1 次尝试）` → `上线注册已确认（cReplyCode=0）` → `协议线已上线`。

### 环境副作用（重要，别踩第二次）

第一次解除规则后，App 连续约 2 分钟仍失败：`Failed host lookup: 'msfwifi.3g.qq.com' (No address associated with hostname)` +
所有 IP `Connection timed out`，而同一时刻 shell `ping 8.8.8.8` / `ping msfwifi.3g.qq.com` 完全正常，
iptables 里也已没有任何 uid 10372 的规则。`am force-stop` 重启进程后立刻恢复。
推断是 REJECT 触发了 Android netd 的连接惩罚态（`st_clear_detect` / `bw_penalty_box` 那类按 uid 的链），
不是 App 的锅，但也没有正面证据。**下次改用 `-j DROP`，或者测完立刻 force-stop 再起，避免误判成"App 不会自愈"。**

## 2. P1 断网期间消息补回（私聊）

| 时间 | 动作 | 证据 |
|---|---|---|
| 14:23:00 | 联网对照：TIM 发 `P1-0` | 推送 `type=166` → `拉新消息 消息=1`，落盘 1 条 |
| 14:24:2x | 加规则断网 | `seq=195/196/197 等待响应超时`；`断线恢复：网络不可用` |
| 14:25 | TIM 发 `P1-1`（窗口内） | 文件行数 10 → 10（块内 0 条，符合预期） |
| 14:29:10 | 进程重启后恢复 | `拉新消息 会话块=3 消息=6`，`P1-1` 落盘 |
| 14:31:5x | 再次加规则断网 | 同上，块内文件行数保持 11 |
| 14:32:0x–14:32:4x | TIM 连发 `P1-2``P1-3``P1-4``P1-5` | 每条都核对了输入框已清空（见 §4 坑） |
| 14:32:56.402 | 解除规则 | `断线恢复：第 1/3 次（票据续期）` |
| 14:32:56.834 | 自愈成功 | `断线恢复成功（第 1 次尝试）` |
| 14:32:59.016 | 补拉 | `拉新消息 会话块=3 消息=9`，文件 11 → 15 行 |

**结果：4 条全部补回，零遗漏、零重复。** 落盘 15 行 / 15 个唯一 msgId（`Set(id).size == 15`），
时间戳严格递增（1793428307000 < 8319000 < 8332000 < 8344000），顺序与发送顺序一致。
`P1-1` 在第一次窗口内发出，虽因进程重启延后到 14:29 才落盘，但也补回了（同样只 1 条）。

关于 `消息=9` 与"只多 4 行"：`消息=N` 是各会话块的合计条数，含已存在消息的去重命中；
以后以**落盘行数增量 + msgId 唯一性**为准，不要拿 `消息=N` 当净增条数。

## 3. P2 群历史 `result=104 条数=0` 是否为故障

结论：**不是故障，是"该窗口没有内容可下发"。**

- `PbUnReadMsgSeq` 在 14:29:12 与 14:32:57 两次都返回 `群 486045673 最新 seq=59158`；
- 我方轮询固定请求 `last+1 .. last+20`，即 `59159-59178`，整段都在服务端水位之外 ⇒ 服务端只能回 104；
- 同一群在 13:33 / 13:51 的窗口内有消息时，返回的是 `result=0 条数=20`（上线补拉 59139-59158 实测 20 条）。

=> 代码把 `0/104` 当"窗口内无新消息"是对的（`lib/client_api/qq8_login_service.dart:2101-2117`），**不需要改逻辑**。
唯一可选的降噪：这行日志每 16 秒打一次且形似错误，可降级或只在 result 非 0/非 104 时打（未改）。

## 4. 踩坑

- `adb shell input text` 之后 `发送` 按钮只在输入框有文字时出现，且键盘弹出会让底部控件位置变化。
  第一轮我按固定坐标点"发送"，实际四次都没点中，四条消息全堆在草稿里（输入框里是 `P1-2\nP1-3\nP1-4\nP1-5`），
  **差点误判成"服务端丢消息"**。正确做法：每次发送后 dump 一次，确认 `id/input` 的 text 回到占位符才算发出。
- 只要 UI 自动化在发消息，就必须先证明"发送方真的发出去了"，再看接收方有没有收到；否则测的是自己的手抖。
