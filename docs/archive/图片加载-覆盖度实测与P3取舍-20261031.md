# 图片加载：覆盖度实测与 P3（富媒体下载）取舍

日期：2026-10-31　设备：25091RP04C / Android 16 / release 包 / uin 3880159487

## 1. 为什么要测覆盖度

P0+P1 做完（失败分类 / 负缓存 / 退避 / 状态 UI），P2 证明**重拉历史拿不到新 rkey**（见
`docs/图片直链刷新实验-P2结论-20261031.md`）。剩下唯一的问题是量化的：

> 在我们能做到的手段之内，聊天记录里的图片到底能看回多少？剩下的为什么回不来？

不能靠"感觉"回答，所以直接对落盘数据与本地缓存做对账。

## 2. 对账方法与结果

数据源（真机拉取，只读）：

- `files/accounts/<uin>/chats/group_486045673.jsonl`：86 条消息
- `files/accounts/<uin>/media_index.json`：缓存索引（键 = `img:<file 名>`，14 条）
- `files/accounts/<uin>/media/photos/`：14 个文件，合计 7.1 MB

判定：消息里的 `segments[].data.file` 与索引键 `img:<file>` 命中即"本地可看"。

| 日期 | 图片条数 | 本地命中 | 签名直链（含 rkey） | 无签名（只有 md5/ids） |
|---|---|---|---|---|
| 2026-10-30 | 3 | 2 | 1 | 2 |
| 2026-10-31 | 18 | 12 | 10 | 8 |
| **合计** | **21** | **14（67%）** | **11** | **10** |

关键交叉结论：

- **11 张签名直链 100% 全部命中**（10-30 的 1/1，10-31 的 10/10）⇒ 「收到即预取」这条链路是通的，`chat_store.dart:588 _prefetchMedia`（插入消息后 :1161、开会话时 :1358）确实在工作。
- **7 张未命中的，无一例外都是不带 rkey 的形态**（`gchatpic_new/0/0-0-<MD5>/0`）。不是我们没去下，是那个地址本身就取不到。
- 另有 3 张无签名形态（`gchatpic_new/<数字>/<ids>-<MD5>/0?term=2`）**命中过** ⇒ 无签名不是一律死，带完整 ids 的还能取。

## 3. 那 7 张死链：换形态能不能救？

拿 7 张里可复现的样本，穷举客户端唯一能构造的候选形态（无 rkey、无 ids 的前提下）：

| 候选形态 | 结果 |
|---|---|
| `gchatpic_new/0/0-0-<MD5>/0` | 404 |
| 同上 `?term=2` / `?term=2&is_origin=1` / `?term=2&is_origin=0` / `?spec=0` | 全 404 |
| `gchatpic_new/<发送者uin>/0-0-<MD5>/0` | 404 |
| `gchatpic_new/<发送者uin>/<发送者uin>-0-<MD5>/0` | 404 |
| `gchatpic_new/0/<发送者uin>-0-<MD5>/0` | 404 |

7 张 × 5 形态全部 404；再叠加 P2 的结论（去掉 rkey → `-5503010 invalid rkey`；改 spec → `-5503037 invalid spec or format`）。

**结论：这些地址缺的是服务端侧的 fileid/rkey/完整 ids，客户端无法凭空造出来，服务器也不给。到此为止。**

## 4. 所以 P3（富媒体下载）是唯一剩下的路，但代价很大

官方能力：`ImgStore.GroupPicDown` / `LongConn.OffPicDown`（常量见
`analysis/_decompiled/jadx9360/sources/com/tencent/mobileqq/transfile/RichMediaConstants.java`）。

取证遇到的硬障碍（本轮实测）：

1. **官方组包代码不在手上**：`com/tencent/mobileqq/transfile` 包只在 jadx9360 的常量里出现过一次，jadx8/jadx11/jadx8950 都没有该包；jadx-main 只反了 msf/wtlogin 子集。本机没有 jadx CLI（只有 `skylot/jadx` 的 GUI cache 目录），要补就得先解决"反编译哪个类"——而类名正是缺失信息。
2. **公开实现没有下载侧**：ricq-core 0.1.19 的 `command/img_store/builder.rs` 只有 `build_group_image_store_packet`（= `ImgStore.GroupPicUp` 上传，`D388ReqBody{net_type:3, subcmd:1, tryup_img_req:[...]}`）；oicq-src 只有上传 + 直接吃 http 直链（`lib/message/image.ts` 的 DownloadTransform 只用于发送本地文件）。mirai 的 `ImageDownPacket` 在公开镜像上取不到（Anubis 拦截 / raw.githubusercontent / jsdelivr 都不含 qqandroid 时代文件）。
3. 即使补齐组包，还要实现：高优通道（highway）包头 + 分片 + token 透传 + 断点续传 + 校验，且**必须真机反复试错**（协议层没有离线断言手段）。工作量按"天"计，且失败风险实质存在。

## 5. 取舍建议

**建议接受现状，不做 P3。** 理由：

- 67% 是"能取到的全取到了"的结果，不是实现缺陷：11/11 签名直链全命中。
- 缺的 33% 不是"我们没做"，而是"服务端没给可取地址"，靠客户端任何 HTTP 技巧都补不上（本报告第 3 节 + P2 已两轮证伪）。
- 缓存策略已经足够宽：`chat_store.dart:112 maxCacheBytes = 512MB`，`keepMediaFor` 默认 null = 永久保留（只受上限约束），所以**只要当时取到了，就一直在**。
- 失败态已经有明确文案（`图片已失效 · 点按重试`），不会让用户对着空白框猜。

如果哪天确实要 100% 可回看，唯一的路就是 P3，且应先做一件事：**用 jadx 反编译 8.2.11/9.3.60 的 `transfile` 相关类，确认 `GroupPicDown` 的请求/响应结构**，再评估。在那之前继续投入是盲试。

## 6. 四态口径

- 已实现：失败分类、负缓存、退避重试、状态 UI、头像重试、"收到即预取 + 512MB 永久缓存"。
- 离线已验证：直链刷新不可行（P2）；7 张死链 15 种形态全 404（本报告）；缓存索引与消息对账 14/21。
- 真机已验证：签名直链 11/11 命中（对账推断 + 设备 `media/photos` 14 个文件 7.1MB）；失效占位文案 `图片已失效 · 点按重试` 实际出现在群聊页。
- 明确不支持：`ImgStore.GroupPicDown` / `LongConn.OffPicDown` 富媒体下载（无组包代码、无公开参考）；客户端自造 rkey（`-5503010`）。
